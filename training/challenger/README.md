# Learned challenger protocol

This experiment adds a second policy. The operator chooses a tool call. The challenger chooses a scenario family and opening demand band for the next shift. It learns by interacting with the operator throughout training. The existing environment, operator features, operator reward, and first published experiment remain fixed.

## Design fixed before testing

- Train fresh operator pairs with seeds 101, 211 and 307. Both members start from zero weights, use the published 34-feature REINFORCE operator, update every 24 completed episodes and receive **exactly 32,768 operator tool calls**. Both train from the same fixed scenario bank within each pair. One samples cells uniformly, the other follows a learned challenger.
- The ten cells cross five families (normal operations and four single disruptions) with ordinary (28 or fewer) or high (29 or more) opening demand. Per training replicate, fill each cell with its first 160 matching seeds starting at 4,000,000 plus 10,000 times the zero-based replicate index. Every member must have a successful audited witness schedule. A cached witness is common to both members. Each selected episode samples one bank entry with replacement. Training code records the shared witness calls and CPU cost separately.
- The challenger has ten trainable logits. It uses a categorical policy with 20% uniform exploration. Challenger reward is the binary gap between its feasible witness's complete success and the current stochastic operator's verified complete success. Each completed shift produces one REINFORCE update with a moving reward baseline, learning rate 0.09 and a 0.10 entropy bonus on the underlying softmax. This learns to find feasible cases the operator misses. Maximizing failure is not the same objective as maximizing subsequent learning progress.
- Updates use only completed training shifts. At the final call cap, the partial shift is excluded from gradient estimation; all of its calls are charged. Apply the final incomplete optimizer batch using all its completed shifts. Record the mix, logits, episode counts and training timings at every 4,096 calls. Record validation performance using the current updated weights at the exact call milestones, and after the final flush at the last milestone.
- Validate on 60 new scenarios using training families and seeds 5,000,000 through 5,000,011. The prespecified threshold is 85% strict episode success. Use final checkpoints regardless of validation scores. Evaluate on 168 fresh scenarios using seeds 6,000,000 through 6,000,023 in all seven families, including the two unseen combinations. Report paired replicate outcomes, held-out strata and the dispatcher's performance. Final-test cases are disjoint from every previously published suite.
- Preselect training seed 101 for the public challenger. A visitor seed samples one cell using its learned final probabilities and generates a fresh matching scenario. The browser verifies a feasible witness before returning it. This policy acts only at scenario selection. The operator receives ordinary limited observations.
- Count training, validation, feasibility verification and final evaluation separately. Operator environment interactions have an exactly matched budget. CPU timings are observations on one machine. Three paired runs cannot establish a general curriculum acceleration result.

## Reproduce

Run `node training/challenger/run.mjs` from the repository root. It trains both conditions, evaluates the frozen final checkpoints and writes evidence to `docs/data/challenger/`. Run `node training/challenger/audit.mjs` to regenerate trial histories, probability updates and held-out outcomes and compare them with the published artifacts.
